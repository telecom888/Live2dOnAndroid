# 设置二级页、Line Mode 与消息分支设计方案

状态：方案及实施记录（2026-09-25）。参考图为用户提供的两张聊天截图；截图中的视频播放器顶栏、点赞栏、关注按钮和底部弹幕控件不属于目标聊天 UI。

## 1. 范围与现状

| 需求 | 当前实现 | 本方案目标 |
| --- | --- | --- |
| 设置二级页 | 桌面壁纸、交互、渲染、语音由 `SettingsScreen` 内部路由展示，复用 `SettingsDetailPage`；LLM 设置由 `LlmSettingsActivity` 单独承载，虽有相似顶栏但导航方式不同。 | 五个入口统一顶栏、内容边距、进入和返回动画；返回设置主页时保持原滚动位置。 |
| 个性化 | 设置页目前有 LINE 外观开关与头像设置，但缺少消息时间、日期、朗读与重试图标的展示偏好。 | 增加“个性化”二级页，集中设置聊天展示偏好；其导航与滚动行为也遵守第 2 节。 |
| Line Mode 外观 | “设置 → LINE 风格聊天界面”控制普通聊天消息的 `lineMode` 渲染；头像、气泡仍大体使用 Material 主题色，时间和已读放在气泡内。 | 仅开启 Line Mode 的聊天界面采用参考图的蓝底、黄/白气泡和头像排版。关闭时保持现有普通聊天样式。 |
| 聊天输入与模型时间 | 消息气泡只显示本地短时间；模型请求没有明确的发送时刻。聊天详情页与 Live2D 浮层分别处理输入法避让。 | 展示时间与发送给模型的时间分别可控；输入框贴近输入法，消除异常大块空白。 |
| 消息编辑与重新生成 | `ChatConversation.messages` 是线性列表；`retry()` 仅重试上一次失败请求。聊天详情页和 Live2D 聊天浮层共用 `ChatMessageList`。 | 我方消息可长按编辑并重发；同一位置的用户版本、助手回复版本均可切换，旧分支永久保留。 |

这里的 **Line Mode** 指设置开关 `loadLineUiEnabled()` 控制的聊天外观，涉及 `ConversationManagerScreen` 与 `Live2DChatOverlay`。项目另有独立的 `LineScreen`（角色之间自动讨论的旁观页）及 `LineMessage`/`LineSceneRepository`，不是用户与助手的聊天历史；本轮外观规范不强制迁移其数据或加入编辑重发功能。如果希望旁观页也套用同一视觉，可在主聊天实现后复用视觉组件，但仍维持其独立交互。

## 2. 设置二级页统一规范

### 2.1 页面骨架

现有五个二级页和新增“个性化”页都使用同一页面规格：顶栏固定在顶部，左侧返回按钮、中间标题及最多一行说明；内容区独立纵向滚动，沿用当前主题、液态玻璃开关和状态栏安全区；左右内容边距 16dp、卡片间距 12dp、底部留足系统导航安全区。空、加载和错误状态不改变顶栏的位置。LLM 页也按此规格处理，不能只统计 `SettingsDetail` 枚举中的四页。

顶栏标题、返回图标、卡片圆角、背景与文字对比度、触控热区要由共同的二级页容器约束；各页只提供标题、副标题和内容。LLM 页目前在独立 Activity 中，存在两种可行实现：

1. **建议：并入设置页内部路由。** 将 LLM 表单内容抽成可复用的页面内容，并复用二级页容器。这样进出动画、返回手势、父列表状态可由同一导航状态管理。需保留原 Activity 入口的兼容处理，避免应用内其他入口失效。
2. 如暂时保留 Activity，则统一其页面容器和 Activity 进入/退出过渡；启动前记录设置主页列表状态，Activity `finish()` 后恢复。需要额外覆盖系统返回手势、进程重建和启动器回到应用的场景。

### 2.2 统一动画

进入二级页：子页从右侧轻量滑入并淡入，设置主页向左小幅移动并淡出；返回时完全反向。动画使用项目已有 `MotionTokens.kt`：进入 `emphasizedTween()`（300ms）、退出 `expressiveTween()`（180ms），位移幅度与 `LineScreen` 的层级切换保持同一量级，不做整屏夸张位移。系统返回按钮、顶栏返回和预测性返回手势要得到同样的视觉结果；减少动画设置启用时应尽量直接切换。

切换期间父页内容与二级页内容保持各自状态，不重新初始化页面；避免连续快速点按造成重复打开或“返回两级”。页面交互在过渡结束后恢复正常焦点。

### 2.3 返回时保留滚动位置

设置主页只创建一个可保存的 `LazyListState`，由 `SettingsScreen` 的导航宿主拥有并传给 `SettingsHomeList`，记录首个可见项的稳定 key/索引与偏移量。进入子页前不清空；返回后恢复到原位置，**不能滚回顶部**。配置变化与 Activity 重建使用可保存状态；跨 LLM Activity 时也需保持父 Activity 的同一列表状态。调整字体、窗口大小或设置卡片数量导致原位置失效时，恢复到最近的有效项并限制偏移量。

每个二级页也应保存自己的滚动位置：临时离开并返回同一页时恢复；从设置主页重新打开页面时可按产品预期从上次位置继续，至少不能让主页跳动。验收需覆盖滚到“语音”后进出现有五个入口与新增“个性化”入口、系统返回、顶栏返回、横竖屏和进程重建。

### 2.4 推荐改动位置

- `ui/settings/SettingsScreen.kt`：导航状态、共享二级页容器、主页 `LazyListState`、各子页内容。
- `ui/settings/LlmSettingsActivity.kt`：若合并路由，改为兼容入口；若保留 Activity，统一过渡并协调父页状态。
- `MainActivity.kt`：二级页激活时的外层顶栏、水平边距和底部导航显隐要与统一动画同步，避免切换时闪动。

## 3. Line Mode 聊天视觉规范

### 3.1 参考图可确认的元素

第二张截图是较清晰的聊天区域裁图，可作为气泡与排版主参考；第一张截图补充整体视觉。参考图聊天底色采样约 `#AAC2D3`，我方气泡约 `#FFE327`，对方气泡为白色。这些颜色先作为设计起点，最终要在设备上按实际截图和文字可读性微调，不直接把视频平台叠加的半透明文字当作聊天 UI。

| 元素 | 目标 |
| --- | --- |
| 聊天背景 | 整个消息列表为稳定的浅灰蓝色；不能只给单条消息着色而露出主题默认背景。顶部栏与底部输入区应衔接同一色系。 |
| 我方消息 | 右对齐、亮黄色圆角气泡、深色正文；靠外侧有短尾角；不显示我方头像。时间显示开启时，将时间放在**气泡左侧靠下、气泡外部**，如参考图的 `07:00`。 |
| 对方消息 | 左侧圆形角色头像，头像右侧显示当前角色名称；消息为白色圆角气泡，短尾角朝头像。时间显示开启时，将时间放在**气泡右侧靠下、气泡外部**。 |
| 连续消息 | 同一角色短时间连续发送时可合并头像/名称占位，但消息仍逐条显示，间距明显小于不同发送者之间的间距。不能因隐藏头像造成气泡左右抖动。 |
| 顶栏 | 返回键、当前角色名称与必要操作保持简洁；不要复制视频截图中原作者或播放器的控件。 |
| 输入区 | 背景与聊天区域自然衔接，输入框/发送按钮有足够对比度；输入法弹出时不遮挡最后一条消息和版本切换控件。 |

头像来源应沿用 `AvatarManager`：角色自定义头像优先，随后默认角色头像；读取失败用稳定的角色首字/占位头像，不能显示破损图。参考图的“瓶子照片”只是示例角色头像，**不应把截图头像裁出作为所有角色的默认头像**。我方头像在参考图的聊天区域并未出现，因此 Line Mode 的我方消息不显示现有 `userAvatar`；用户设置中已配置的我方头像保留在设置页，不删除数据。

普通模式继续遵守应用主题。Line Mode 的这组三色应作为专用设计令牌，并提供暗色模式下可读的对应颜色；文字对比度、长文本、图片消息、日文/中文混排、字体放大以及高对比度设置要在真机预览中检查。气泡最大宽度维持合理范围（约屏宽 80%～85%）；宽屏仍受现有最大宽度限制。不要直接使用截图像素尺寸作为 dp。

### 3.2 当前实现与落点

`ChatMessageList` 和 `ChatBubble` 位于 `ui/live2d/Live2DChatOverlay.kt`，普通聊天详情与 Live2D 聊天浮层都调用它们。因此视觉组件应在此共用，而列表背景、顶栏和输入区需要两个宿主分别接入 Line Mode 配色。`LineScreen.kt` 的角色旁观页目前是第三套布局；不把它误认成“LINE 风格聊天界面”的开关目标。

参考图对“已读”的位置并不充分明确：建议沿用现有已读语义，但移到我方气泡左侧与时间成一组；我方已读状态改变不应改变气泡宽度。时间与气泡外缘保持约 4～8dp，底部对齐；短消息、长消息、连续消息和大字号下都不能重叠或跨屏。语音朗读、图片预览、搜索高亮与流式生成提示必须在新气泡上继续可用。

## 4. 个性化、时间与输入法

### 4.1 设置页新增“个性化”入口

“设置 → 个性化”作为新的二级页，沿用第 2 节统一页面容器与动画。建议把现有 LINE 外观开关及头像展示选项也整理到此页的“聊天外观”分组，避免设置主页同时存在两套聊天外观入口；迁移只调整入口，不清除已有偏好和头像。新增控件：

| 控件 | 建议默认值 | 范围和规则 |
| --- | --- | --- |
| 聊天中显示消息时间 | 开（保持现有可见行为） | 控制普通模式与 Line Mode 的**消息气泡时间**，不影响消息实际时间戳、会话列表排序或模型收到的时间。关闭时不留下空白占位。 |
| 时间中显示月/日 | 关（保持参考图的 `07:00` 样式） | 仅在“显示消息时间”开启时可操作。关闭显示本地 `HH:mm`（按系统 12/24 小时习惯）；开启显示本地 `月/日 HH:mm`，不显示年份。跨年消息可在详情中看到完整日期，避免歧义。 |
| 聊天中显示朗读按钮 | 开（保持当前聊天详情页行为） | 只控制助手消息旁的朗读入口是否可见，不关闭语音功能本身。普通模式与 Line Mode 一致；浮层目前没有朗读入口，若后续加入也应遵守同一偏好。 |
| 聊天中显示重试图标 | 开（保持浮层错误提示中现有图标行为） | 控制聊天里的重试快捷图标，以及新增助手消息“重新生成”快捷图标；不影响失败请求重试和助手重新生成能力。隐藏图标后，失败提示仍提供文字“重试”操作，助手消息仍可经长按菜单重新生成。普通模式与 Line Mode 使用同一偏好。 |

这些展示选项独立于 LLM 设置里的“发送时间给模型”；**隐藏 UI 时间不等于禁止发时间给模型，显示 UI 时间也不代表模型收到时间**。偏好修改后当前聊天立即更新，不改写历史数据。月份/日期格式由设备语言环境和时区处理，示例只说明信息量；不要用固定英文格式覆盖中文、日文等地区习惯。

时间、已读、朗读与重试图标是独立元素。Line Mode 按截图将我方时间放气泡左下、对方时间放气泡右下；朗读和重试快捷图标应放在独立操作区域或更多菜单中，不能把时间推回气泡内，也不能因开关变化导致气泡抖动。时间关闭而已读开启时，只显示已读且紧贴气泡；两者都关闭时气泡外不保留空行。普通模式沿用其布局，但也应避免时间与操作按钮混在同一行后错位。重试图标开关不控制消息版本的 `‹ 2/3 ›` 切换器。

### 4.2 LLM 设置增加“发送消息时附带时间”

LLM 设置页新增独立开关，建议文案为“发送消息时附带时间”，副说明：“让角色知道你发送这条消息时的本地日期、时间和时区；扮演 BangDream 世界中的角色且不与现实同步时建议关闭。”默认**关闭**，延续现有请求行为；在现实时间同步的用户身份聊天中由用户开启。为了同一设备上可同时进行两类聊天，建议会话菜单再提供“跟随 LLM 全局设置 / 此会话开启 / 此会话关闭”三态覆盖，覆盖值随会话保存。没有设置覆盖值的旧会话跟随全局值。

时间来源为消息**实际发送成功提交时**的设备本地时钟，并记录时区偏移或时区 ID；模型上下文中使用明确的日期与分钟精度，例如 `2026-09-24 23:15 (UTC+08:00)`。它是请求元数据，不拼进用户可见正文，不让聊天气泡出现一段系统注释。具体可在组装 LLM 请求时为当前路径上“启用附带时间”的用户消息添加清晰标记，或者加入专门的临时上下文段；必须保持系统提示词与用户正文边界清楚，避免把时间误认成角色发言。关闭时请求中不能残留任何自动注入的真实日期/时间。

时间附带状态应在每次发送时随该消息/分支记录：之后切换全局开关，不能把旧消息追溯改成“当时带了时间”。编辑并重发会创建新消息节点，按**新提交时刻**和该会话当前设置决定是否附带；对旧用户消息重新生成助手回复时沿用该消息原先记录的时间与设置，不用重新生成当下的现实时间改写历史情境。模型时间与 UI 的显示时间都以同一底层时间戳为来源，但用途和开关互不影响。设备时间或时区变化时已记录消息仍保持其发送时刻；如用户希望修改世界观时间，应通过聊天内容或未来的剧情时间设置表达，而不是强制跟随真实时间。

验收场景：同一角色有一个现实同步会话和一个 BangDream 角色扮演会话；前者请求含正确本地时间，后者请求不含自动时间；二者的 UI 时间显示偏好可相同。切换偏好、离线重试、编辑旧消息与回复重新生成均不造成时间注入重复或泄露其他分支的时间。

### 4.3 输入框与输入法间的大块空白

要分别核查聊天详情页与 Live2D 浮层。聊天详情页的 `ConversationDetailScreen` 使用 `.imePadding()`，而 `MainActivity` 的外层 `Scaffold` 始终有 `NavigationBar` 并对内容应用 `padding`；底部栏保留空间、系统导航栏与 IME inset 可能叠加。浮层的 `Live2DChatOverlay` 又用 `WindowInsets.ime`、可见窗口边界和 `bottomPadding = 16.dp + imeOverlap` 计算位置，再给内部内容 12dp padding。**这些是代码中的待核查点，不先断言唯一根因。**

实施时先在键盘弹出前后测量输入框底边、输入法顶边、系统导航栏和各层实际 inset；同一个 IME 空间只由一层消费。详情页在键盘出现时不应继续为不可见底部导航栏保留整栏高度；浮层应按“窗口是否已被 `adjustResize` 缩小”决定是否还需要额外上移，避免重复加入 `imeOverlap`。保留约 4～8dp 的视觉间距以及可点击的发送按钮热区，不把输入框压进键盘里。

验收：不同输入法（至少系统默认与另一款）、三键/手势导航、普通模式/Line Mode、单行/多行输入、图片附件预览、聊天详情页/Live2D 浮层、横竖屏均无明显空白带；键盘收起后布局准确复位，最后一条消息与发送按钮不被遮挡。

## 5. 编辑重发与回复版本：数据模型

用户给出的 C++ `vector<vector<string>>` 很好地表达了“一个位置可以有多个版本”，但真实聊天还会有连续用户消息、历史消息编辑、图片、流式回复、跨版本上下文和后续消息。单纯按用户/助手两个二维数组索引配对容易错位。建议在现有对话之内使用**消息节点树 + 当前选中路径**：

- 每个节点保留 `id`、`parentId`、`role`、正文、时间、图片引用、reasoning、已读以及生成状态。节点 `id` 永久稳定。
- `parentId` 指向这条消息生成时所依赖的上一条消息；同一父节点下的多个 `user` 节点是同一位置的编辑版本，同一父节点下的多个 `assistant` 节点是该上下文的回复版本。
- 对话记录 `activeLeafId`（当前选中分支的末端）、每个分叉点的 `preferredChildId`（上次选择的后续节点）和格式版本号；UI 展示从根到该叶节点的一条路径。完整节点树仍保存全部旧分支。
- **“单向总计消息数”改为当前路径的消息数**；另可统计全树节点数，但不能让隐藏分支进入当前上下文、搜索结果或当前会话的预览。

示意：

```text
U1 原文 ─ A1 原回复 ─ U2 后续消息
  ├── A1' 重新生成的回复
  └── （U1 的编辑版本是从 U1 的父节点分出的 U1'）
U1' 改写后 ─ A2 新回复 ─ U3 新后续消息
```

实现时根节点可为虚拟节点；同一父节点下的候选消息按创建时间排序，并使用稳定 ID 作为并列排序依据。用户在某个消息位置选旧版本时，沿该版本的 `preferredChildId` 链切到**该版本最近一次使用的后续路径**；若该版本从未继续对话，当前路径就在该节点结束。随后发送新消息或生成回复，形成新的后续节点。不能将其他分支的旧回复接到已编辑的用户消息后面。

### 5.1 操作语义

1. **长按我方消息 → 编辑。** 弹出编辑器，预填该版本正文；取消不改变历史。保存并重发时创建新的用户节点作为原节点的兄弟版本；原节点及时间不变，新节点取得新 ID 和时间。切换到新路径，并仅用“原消息之前的当前前缀 + 新文本/新图片”请求模型。原消息之后的旧回复与后续对话仍保存在旧分支。
2. **长按助手消息 → 重新生成。** 不改用户消息，在相同父节点和相同历史前缀下创建一个新的助手候选。新回复完成后切到它；旧助手版本与它原本的后续对话保留。
3. **点击版本控件切换。** 有多个候选时在相应气泡下显示 `‹ 2/3 ›`；我方控件切换用户版本，对方控件切换助手版本。切换不触发 API 请求、不执行历史回复中的动作标签、不篡改旧消息。弹出简短提示说明切换会显示对应分支的后续消息。
4. **正在生成时。** 禁止重复提交编辑/重新生成；若要从历史位置分支，先显式停止当前生成并等待流与持久化收尾，再建立分支。避免晚到的流式结果写入已切走的路径。历史切换时清空仅属于上一请求的流式占位。
5. **失败时。** 已保存的用户新版本保留并显示失败状态，允许在该版本上“重试生成”；没有正文的失败助手不占用可切换版本号。若有部分有效回复，明确标记为中断版本并允许重新生成。现有 `retry()` 是失败请求重试，不等同于正常的“重新生成”。

建议将“编辑”和“重新生成”作为消息菜单操作，避免与文本长按选择复制冲突；仍应提供复制、朗读等已有操作。编辑器明确标示“编辑后将从此处生成新分支”，可编辑文本与当前消息携带的图片。若旧图片只有临时 base64、无法恢复，必须先处理图片的持久引用或在 UI 上说明并禁止无声丢图；不能悄悄按纯文本重发。

### 5.2 请求与存储边界

- 向 `LlmChatClient` 发送的只能是当前选中路径上的 `user/assistant` 内容，按路径顺序排列；系统提示词、角色设定、长期记忆的现有构造方式保留。切换旧分支后，新消息必须基于旧分支上下文继续。
- `ChatHistoryRepository` 已使用原子写入。新格式应把节点、活动路径指针和会话元数据放在同一对话持久化事务中，避免崩溃后指针引用不存在的节点。旧线性 JSON 首次加载时按原顺序串成一条链，写新格式前保留可恢复的旧数据或完成一次可靠迁移。未知格式版本不能被空对话覆盖。
- `ChatUiState.messages` 可以继续作为“当前路径的扁平投影”，供现有列表、搜索与滚动使用；仓库保存完整分支树。会话摘要、消息数、token 估算、全文搜索、导出/记忆读取默认只看当前路径，并在用户切换版本后刷新。
- 新节点生成与持久化需要按对话串行化；UI 请求带目标对话 ID、父节点 ID 与一次性请求 ID，晚到的网络结果只可落到其原定分支，不能污染正在看的另一分支。是否自动切到后台完成的分支，要有固定规则；建议仅在用户仍停留在该请求上下文时自动切换。
- 已读状态属于具体用户消息版本；编辑后的新版本初始未读。历史切换不能重放已发生的外部动作，角色动作/语音等副作用按助手消息 ID 去重或仅对当前实时生成触发。
- 对话删除清理全部节点；会话标题若自动取首条用户消息，可随活动路径更新，手动改名的标题不随分支切换改动。

### 5.3 预期验收示例

1. `U1 → A1 → U2 → A2` 中编辑 `U1` 为 `U1'`，产生 `U1' → A1'`；旧的 `U1 → A1 → U2 → A2` 能完整切回。
2. 在 `U1'` 下对 `A1'` 连续重新生成两次，显示 `1/3、2/3、3/3`；每次请求历史都只包含 `U1'` 所在前缀，不包含其他两个助手版本。
3. 从旧 `A1` 继续发送 `U3`，新消息挂在旧分支；切回 `A1'` 不出现 `U3`。
4. 编辑最后一条我方消息、取消编辑、生成失败后重试、生成途中停止、切换角色或会话、关闭并重启应用后，版本数与当前路径一致，不重复生成或丢失旧分支。
5. 搜索、会话预览、消息数与 token 估算只反映当前路径；图片消息、已读、朗读和 Line Mode 外观仍正常。
